🔴 1. Biggest issue: your credit accounting can be abused

This is the first thing I'd fix.

Your /api/generate endpoint checks whether the user has credits before generation, then calls the AI provider, and only afterward deducts the actual tokens_used.

That creates a concurrency race:

Request A → sees 5,000 credits
Request B → sees 5,000 credits
Request C → sees 5,000 credits
...

Multiple simultaneous requests can all pass the balance check before the database has been updated.

For a paid API product, that's dangerous.

Fix

Implement an atomic reservation/debit mechanism.

Something conceptually like:

BEGIN TRANSACTION

UPDATE users
SET credits = credits - estimated_cost
WHERE id = ?
AND credits >= estimated_cost

IF affected_rows != 1:
    reject request

COMMIT

Then reconcile the actual token usage afterward.

I'd also put a per-user rate limiter around /api/generate.

🔴 3. Stripe webhook needs idempotency

This is a major SaaS accounting issue.

You process:

checkout.session.completed
invoice.payment_succeeded
customer.subscription.created
...

but I don't see an event-idempotency mechanism in the billing implementation.

Stripe can retry webhook delivery.

That means a webhook can potentially be delivered more than once.

For credit packs, this is particularly dangerous:

user.credits += tokens

If the same successful checkout event is processed twice:

25,000
→ 50,000

without the customer paying twice.

Fix

Create something like:

stripe_events
----------------
event_id UNIQUE
event_type
processed_at

Before processing:

if event_id exists:
    return already_processed

insert event_id

process transaction

commit

This should be considered mandatory before serious revenue volume.

🔴 4. Your checkout URLs are user-controlled

Your models accept:

success_url: str
cancel_url: str

directly from the client.

Then those values go into Stripe Checkout.

That's unnecessary attack surface.

A malicious client can supply arbitrary URLs.

Better architecture

Don't accept them from the browser.

Use:

APP_BASE_URL

server-side:

success = APP_BASE_URL + "/dashboard?payment=success"
cancel  = APP_BASE_URL + "/dashboard?payment=cancelled"

Much cleaner.

🟡 11. Your /admin/trigger-seo protection needs improvement

You currently use a secret query parameter:

/admin/trigger-seo?secret=...

The secret itself can therefore appear in:

browser history

reverse-proxy logs

server logs

analytics

copied URLs

I'd replace this with an authenticated admin endpoint using a header:

Authorization: Bearer <admin-token>

or, better, an admin JWT/role.

🟡 12. Scheduler architecture will eventually bite you

You start APScheduler inside the FastAPI application's startup process.

That works fine on a single instance.

But when you scale horizontally:

Instance A → scheduler
Instance B → scheduler
Instance C → scheduler

you can get:

3 SEO articles
3 email campaigns
3 Reddit scans
3 revenue reports

at the same scheduled time.

Eventually move scheduled jobs to:

Render cron jobs

a dedicated worker

Celery/RQ

a queue system

or another distributed scheduler

For your current scale, it's okay.

For real scale, change it.
